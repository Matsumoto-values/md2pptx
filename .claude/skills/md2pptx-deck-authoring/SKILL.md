# md2pptx 用 Markdown の作成

元資料（レポート、分析結果、議事録、メモ）を、md2pptx が PowerPoint に変換できる
Markdown に書き換える。

**このスキルの範囲は md を書くことだけ。** pptx の生成はパイプライン側が
決定論的に行うので、レイアウトや配色を md に書き込もうとしないこと。
配置はテーマ（テンプレート）が決める。

## 手順

1. **元資料を読み、スライド構成を先に決める**（下記「構成の作り方」）
2. **md を書く**（下記「記法」）
3. **`python3 tools/lint_md.py <md> <theme_id>` を実行する** ← 省略しないこと
4. ERROR が出たら直して再実行。ERROR が消えるまで繰り返す
5. WARN は読みやすさの目安。意図があれば残してよいが、理由を説明する
6. 生成を頼まれている場合は pptx を作る（下記「生成」）

lint は実際にブラウザで描画して座標を測るので、「収まるかどうか」は
推測ではなく実測で判定される。**目分量で判断せず必ず lint を通すこと。**

## 記法

````markdown
# 見出し                      ← 各スライドに必ず1つ
本文の段落。空行で区切ると別の段落になる。
- 箇条書き
!! 装飾バッジ（1枚に1つまで。要点の強調に使う）

> インタビューの逐語引用      ← 発言をそのまま
-- 30代女性・3ヶ月で解約      ← 直後の -- 行が話者の属性になる

| 指標 | 前期 | 今期 |     ← 表。区切り行 | --- | が必須
| --- | --- | --- |
| 売上 | 1200 | 1480 |

```chart
type: column                  ← column / column_stacked / bar / line / pie
categories: [Q1, Q2, Q3]
series:
  - {name: 実績, values: [10, 20, 30]}
  - {name: 目標, values: [12, 22, 32]}
```

```flow
direction: vertical           ← 省略時は横並び
見出し: 本文                   ← 「見出し: 本文」で見出しが小さく太字になる
?判断したい条件?               ← 行頭 ? で菱形（判断）
```

---                           ← スライド区切り
````

**書けないもの**（md に書いても無視される、または崩れる）
- 画像の埋め込み、リンク、脚注、`##` 以下の見出し、太字/斜体の記法
- 表のセル結合、グラフの第2軸、フローの分岐・合流
- 配色・フォント・位置の指定（テーマが決める）

## 1枚あたりの情報量

**実測値**（960x540・本文14px のテンプレートと 1280x720・本文22px の既定テーマ）。
「物理上限」は超えると溢れて ERROR になる境界。「推奨」は資料として読める範囲。

| 要素 | 推奨 | 物理上限(960x540) | 物理上限(1280x720) |
|---|---|---|---|
| 箇条書き | 5〜6行 | 14行 | 11行 |
| 本文の段落 | 1〜2個 | 8個以上 | 8個以上 |
| 表のデータ行 | 8行まで | 10行 | 12行 |
| フローの箱 | 3〜5個 | 7個以上 | 7個以上 |
| グラフ + 箇条書き | グラフ+2行 | +4行 | +4行 |
| 引用 | 1〜2件 | 1件90字以内が目安 | 同 |
| 本文1行の全角文字数 | — | 約60字で折り返し | 約48字で折り返し |

**物理上限まで詰めないこと。** 箇条書き14行は「溢れない」が資料としては読めない。
1枚1メッセージを原則とし、超えたら分割する。

**グラフや表を置く枚は、それ以外をほぼ書かない。** グラフは領域の大半を占めるので、
補足の文は1〜2行に収める。

**見出しは40字以内。** 見出し枠は高さが固定で、折り返すと枠を超えて ERROR になる。

## 定性調査レポートを扱うとき

インタビューやラベル集計を元にした調査報告書が入力になる場合の追加ルール。

**引用は逐語。要約も創作もしない。**
元の md に無い発言を書いてはいけない。長すぎる場合は**切り出す位置を変える**
（言い回しを変えるのではなく、前後を落とす）。
引用には必ず話者の属性を添える（`-- 30代女性・3ヶ月で解約`）。
属性が無い引用は、読み手が代表性を判断できないので価値が下がる。

**n を必ず書く。** グラフや表を置く枚には母数を明記する
（本文に `n=412` を含める）。定性データは母数が小さいことが多く、
n が無い構成比は誤読を招く。lint が警告する。

**ラベル集計は上位5件＋その他に丸める。** 全カテゴリを載せるのは報告書の役割。
スライドでは主要因が見えることを優先する。

**定量で傾向、定性で理由の順に置く。**
- 定量（集計・グラフ）で「何が起きているか」を示す
- 定性（引用）で「なぜそうなるか」を語る
- 逆順にすると、個別の声が全体傾向のように誤読される

**元資料の章立てをそのまま使わない。** 調査報告書は「概要・方法・結果・考察」の
順で書かれるが、スライドは結論から入る。方法論のスライドは、
聞かれたとき用に最後に置くか、そもそも作らない。

## 構成の作り方

元資料をそのまま章立て通りに変換しないこと。**発表資料は読み物ではない。**

1. 元資料から**主張**を抜き出す（何を相手に持ち帰らせたいか）
2. 主張を支える**根拠**を選ぶ（数値、比較、事例）。捨てる判断が重要
3. 1枚1メッセージで並べる。見出しは**結論を書く**
   - 悪い例: 「調査結果」「考察」← 中身が分からない
   - 良い例: 「解約の6割は初月に発生している」← 見出しだけで伝わる
4. 要素の型を選ぶ（下記）

### 内容から要素への対応

| 元資料にあるもの | 使う要素 |
|---|---|
| 時系列の推移 | `chart` の `line` |
| 項目間の比較 | `chart` の `column`（項目が多い/名前が長いなら `bar`） |
| 内訳の合計と構成 | `chart` の `column_stacked` |
| 構成比（1系列・5項目以内） | `chart` の `pie` |
| 複数指標の一覧、前後比較 | 表 |
| 手順、工程、前後の変化 | `flow` |
| 判断分岐を含む手順 | `flow` の `?条件?` |
| インタビューの発言 | 引用（`>` と `--`） |
| 並列する要点 | 箇条書き |
| 前置き、補足、注釈 | 本文の段落 |

**数値がダミーでよい場合を除き、元資料に無い数値を作らないこと。**
元資料に数値が無いなら箇条書きや flow を使う。

### 見出しだけで通読できるか確認する

書き終えたら見出しだけを順に読む。それで話が通じるなら構成は成立している。
通じないなら順序か見出しの書き方が悪い。

## 生成

```bash
# テーマ一覧
ls themes/*.json

# 検証（必須）
python3 tools/lint_md.py deck.md <theme_id>

# 生成
python3 md2html.py deck.md <theme_id> > /tmp/deck.html
python3 extract.py /tmp/deck.html <theme_id> > /tmp/layout.json
python3 build_pptx.py /tmp/layout.json out/deck.pptx <theme_id>
```

`<theme_id>` は `themes/` 配下のファイル名（拡張子なし）。会社テンプレートを
適用する場合はその ID を使う。指定しないと既定テーマ（1280x720）になり、
**テンプレートのキャンバスと食い違って余白がズレる**ので必ず指定すること。

## よくある失敗

- **lint を実行せずに完成とする** ← 最も多い。溢れは目分量では分からない
- 引用を要約して短くする → 逐語性が失われる。切り出す位置を変える
- 引用に話者の属性を付け忘れる → 代表性が判断できない
- グラフや表に n を書かない → 定性データでは誤読の原因になる
- 元資料の章立てをそのまま1枚ずつにする → 情報過多になる
- 見出しに「〜について」「〜の結果」と書く → 結論を書く
- 1枚にグラフと表と箇条書きを同時に置く → 溢れる
- `chart` の `values` の個数を `categories` と揃え忘れる → ERROR
- 表の区切り行 `| --- |` の列数を揃え忘れる → ERROR
- テーマIDを指定せずに生成する → キャンバスが既定値になり余白が崩れる
