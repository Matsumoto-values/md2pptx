# Intent: md2pptx — Markdown から編集可能な PowerPoint を生成するパイプライン

- Status: PoC 完了 / 本実装未着手
- Owner: こーはい君
- Created: 2026-08-05

## 背景と課題

顧客提出用のスライドを Markdown（あるいは LLM の出力）から生成したい。
既存の選択肢はいずれも要件を満たさない。

| 手段 | 問題 |
|---|---|
| python-pptx を直書き | **テキストの折り返し量を計算できない**。枠から溢れても検知できず、目視修正が前提になる |
| HTML/PDF で納品 | PowerPoint での編集ができない。顧客側が数値やコメントを直したい |
| スライド全体を画像化 | 同上。文字が検索・コピーできない |
| Marp / Slidev の PPTX 出力 | 中身が画像化される実装が多く、編集可能な要素にならない |

要点は **「レイアウトは自動で正しく決まってほしい」と「成果物は編集可能であってほしい」の両立**。

## アプローチ

HTML/CSS を**レイアウトエンジンとして利用**し、ブラウザが計算した座標を
python-pptx でネイティブ要素として再構成する。

```
md → 注釈付きHTML → Chromiumで描画・座標抽出 → 中間表現(JSON) → pptx
```

- 折り返し計算・セル幅・段組みは**すべてブラウザに委譲**する。python-pptx はレイアウト判断をしない
- HTML はそのまま**プレビュー**として人間がレビューできる（＝検算手段になる）
- CSS で表現できない装飾は要素スクリーンショットに逃がす（`raster`）
- 表とグラフは**ネイティブ要素**として生成するので、顧客が PowerPoint 上で編集できる

## ゴール / 非ゴール

**ゴール**
- md（+ テーマ定義）から編集可能な pptx を決定論的に生成する
- テナントごとのブランド適用（配色・フォント・余白・表/グラフの体裁）
- 夜間バッチで多数のデッキを生成する（Cloud Run Jobs）

**非ゴール**
- 変換処理自体に LLM を入れること（入力が決まれば出力は一意であるべき）
- PowerPoint の全機能の再現（アニメーション、SmartArt、第2軸など）
- 汎用 HTML→PPTX コンバータ（自前のコントラクトに準拠した HTML だけを対象とする）

## アーキテクチャ

```
job.py          夜間バッチのエントリポイント（Cloud Run Jobs）    ← 主用途
app.py          FastAPI（アドホック要求用 / min-instances=0）      ← 従
renderer.py     変換パイプラインの統合層（上記2つの共通コア）
theme.py        デザイントークン（DEFAULTS → themes/*.json → リクエスト上書き）
md2html.py      md → 注釈付きHTML
extract.py      HTML → 座標JSON（Playwright / BrowserPool）
extract_stub.py 同上のブラウザ無し近似版（CI・開発用）
build_pptx.py   座標JSON → pptx
```

各段は単独の CLI としても動く（UNIX哲学）。段の間は JSON なので差分レビューとデバッグが可能。

### 変換コントラクト

| HTML注釈 | PPTX上の姿 |
|---|---|
| `<section class="slide">` | スライド1枚 |
| `data-pptx="title" / "text" / "list"` | ネイティブテキストボックス |
| `data-pptx="table"` | ネイティブ表（セル座標・列幅をブラウザ実測） |
| `data-pptx="chart"` + `data-chart` | ネイティブグラフ（数値は属性のJSONが正） |
| `data-pptx="shape"` + `data-shape` | ネイティブオートシェイプ（角丸/菱形/楕円など） |
| `data-pptx="connector"` + `data-from` / `data-to` | 図形に接続したコネクタ |
| `data-pptx="raster"` | 要素スクショを画像として貼る |
| 注釈なし | 無視 |

## 意思決定と根拠

### D1. 変換処理に LLM を入れない
入力が決まれば出力は一意に決まる決定論的処理であり、LLM を挟むと遅く・高く・非決定的になる。
非構造な入力から md を書く役目は別サービス（Claude Agent SDK 側）に分離する。
Skill に書くべきは「md記法の仕様」「トークンのスキーマ」「1枚の情報量の目安」であって、
変換の実装知識ではない。

### D2. 表は実測、グラフは実測しない
|  | 座標の出どころ | データの出どころ |
|---|---|---|
| 表 | ブラウザ実測（セル単位） | DOMのテキスト |
| グラフ | ブラウザ実測（外枠のみ） | `data-chart` のJSON |

表はセルの折り返し計算をブラウザに任せる価値が大きい。
グラフは PowerPoint が自前で再描画するため、渡すべきは絵ではなく数値。
HTML側の canvas はプレビュー専用の使い捨てとする。

### D3. デザイントークンを単一の正とする
HTMLプレビュー（CSS）と PPTX ネイティブは別レンダラなので、放置すると体裁がズレる。
`theme.py` のトークンを CSS変数と build_pptx の両方へ注入して二重管理を防ぐ。
テナント単位のテーマは `themes/<id>.json`、リクエストでの部分上書きも可能。

### D4. Cloud Run Jobs を主、Service を従とする
夜間バッチは非同期・コールドスタート許容だが、**待機コストは許容しない**。

| | Service (min-instances=1) | Jobs |
|---|---|---|
| 待機コスト | 常時課金 | ゼロ |
| リトライ | 自前実装 | `--max-retries` 標準 |
| タスク並列 | 自前でスケール制御 | `--tasks` で分割 |
| 実行時間 | リクエストタイムアウトに縛られる | `--task-timeout` で独立 |
| コールドスタート | 避けたい | N件で割れるので問題にならない |

Chromium の起動コスト（3〜5秒）は 1回の起動で全件に償却する。
**デッキ1件ごとに Job を起動する構成は採らない。**

### D5. ブラウザ無しの近似バックエンドを用意する
`EXTRACT_BACKEND=stub` で CSS定数決め打ちの近似レイアウトに切り替わる。
CI でブラウザを用意せず配線を検証するため。**見た目の検証には使えない**ことを明記する。

### D6. フォントは描画側と閲覧側で物理的に同一のものを使う
ブラウザで測った座標が PowerPoint で通用するのは、**両者が同じフォントで組んだ時だけ**。
`theme.font`（pptxに書き込む名前）と `theme.font_stack`（CSSに書く指定）を分離し、
両者が同じ物理フォントに解決されることを必須条件とする。

採用フォントは **BIZ UDPGothic**。Windows 10 1809以降/11 に標準搭載され、
かつ SIL OFL なので Linux（Cloud Run のコンテナ）にも導入できる。
Ubuntu では `fonts-morisawa-bizud-gothic`。

`extract.py` は canvas の `measureText` で monospace との幅を比較し、
意図したフォントで測れているかを実測して警告する。
`document.fonts.check()` は使わない（システムフォントに対して信用できない）。

### D7. プレビューのグラフは自前のインラインSVGで描く
Chart.js 等を CDN から引くと、実行時に外部ネットワークへ依存する。
グラフは**外側の矩形だけが実測対象**で中身は測られないため、描画品質は成果物に影響しない。
`chart_svg.py` でパレット・`gap_width`・`data_labels`・凡例位置を PPTX と同じ
トークンから読んで描画するため、見た目が自動的に揃う。

### D8. フローチャートはネイティブのオートシェイプ＋接続コネクタで作る
「PowerPoint出力後に手で調整したい」というニーズがあるため、この用途では
`raster` に逃がすと目的を達成できない。

- ボックスは `add_shape(MSO_SHAPE.*)` の素のオートシェイプ。塗り・線・テキストが
  すべて通常の図形として編集できる
- 矢印は `add_connector` + **`begin_connect` / `end_connect` で図形に接続する**。
  単に線を置くだけだと、PowerPoint上で箱を動かした瞬間に矢印が取り残される。
  接続しておけば箱の移動に矢印が追従する（手調整用途ではこれが必須要件）
- 矢印の先端は python-pptx に API が無いため `a:ln` に `a:tailEnd` を直挿しする。
  `a:ln` の子要素順序は `fill → prstDash → headEnd → tailEnd` なので、
  **線の色を設定してから** tailEnd を足す（表の罫線と同じ地雷）
- 接続点インデックスは `0=上, 1=左, 2=下, 3=右`。横流れは `3→1`、縦流れは `2→0`

**SmartArt は生成しない**（できない）。SmartArt は OOXML 上で別パート
（`diagramData`）を持つ独自形式で python-pptx は非対応。ただし手で編集する
用途では素の図形のほうが自由度が高いため、実用上の不利益はない。

この機能は**HTML経由の利点が最も出る箇所**でもある。ボックスの高さは中の文字が
何行に折り返されるかで決まるが、python-pptx 直書きではそれを事前に知る方法がない。
flexbox で並べてブラウザに測らせることで、ボックスが中身に応じた寸法になる。

### D9. XMLの要素順序は機械のゲートで守る
`tcPr` の `ln* → fill`、`a:ln` の `... → tailEnd` といった順序違反は、
PowerPoint の「修復が必要です」ダイアログに直結する。これは顧客の信頼を
直接損なう種類の不具合で、しかも**人間のレビューでは検出できない**
（ファイルを開くまで分からず、開いた時にはもう遅い）。

`tests/pptx_check.py` を CI のゲートに置き、Cloud Build の
`ビルド → 検証 → push → デプロイ` の順で、検証に失敗したらデプロイしない構成とする。
検証は**イメージの中でブラウザバックエンドを使って**実行するため、
コンテナ内のフォント解決漏れも同時に捕まえられる。

CI/CD は GitHub → Cloud Build → Artifact Registry → Cloud Run Jobs。
トリガーにはサービスアカウントの明示指定が必要（既定SAがCompute Engineの
既定SAに変わり、Cloud Build Service Account ロールを含まないため）。

### D10. 失敗はデータ起因と環境起因に分けて終了コードを変える
Cloud Run Jobs のリトライは「もう一度やれば直るかもしれない」失敗にだけ意味がある。
テーマ名の誤りや参照先ファイルの不在は何度実行しても同じ結果になるため、
これを非ゼロ終了で扱うと無駄なリトライが発生し、実行全体が失敗扱いになる。

- **データ起因** → 記録して正常終了（`OUT_PREFIX/_failures/<task_index>.jsonl`）
- **環境起因** → 非ゼロ終了して Cloud Run Jobs にリトライさせる
- **判定できない例外は env に倒す**。環境起因を誤って data と判定すると、
  デッキが黙って生成されないまま正常終了してしまうため

判定は例外型ではなく**発生箇所**で行う。同じ `FileNotFoundError` でも、
入力の解決時（mdの参照先が無い）はデータ起因、出力の書き込み時（GCSに書けない）は
環境起因になる。型だけで分類すると必ず誤判定する。

### D11. 会社テンプレートは「ベースファイル + 実測抽出したトークン」で適用する
既存の会社資料（.pptx / 変換後の .potx）をベースとして開き、マスターとレイアウトの
装飾・ロゴ・フッタを継承したうえで、要素は従来どおり絶対配置する。
配色・フォント・余白は**テンプレートから実測抽出**して `themes/<id>.json` にする
（`tools/pptx2theme.py`）。

実際の営業資料3件（自社製品紹介 / 顧客向け提案 / パートナー製品提案）で検証した結果、
当初の設計はほぼ全部間違っていた。以下は実データによる訂正の記録。

**訂正1: テーマ部品（`a:clrScheme` / `a:fontScheme`）は読まない**
3件すべてテーマ部品はOffice既定のまま放置されていた（`accent1=4472C4` / Calibri）。
ブランドデザインは図形の直接書式として入っている。テーマ部品を信じると
generic な Office カラーを拾って完全に外す。

**訂正2: 配色はデザイン層（マスター＋使用中レイアウト）から採る**
スライド側の図形から採ると、注釈（赤い矢印）やコンテンツの色が混ざる。
ある資料では個数順1位が赤い注釈43個、面積順1位が背景の帯で、
ブランド色が候補に出てこなかった。デザイン層から採ると3件すべて正解した。
足りない分だけスライド層から補う二段構えにする。

**訂正3: レイアウトは「実スライドが最も多く使っているもの」を選ぶ**
「プレースホルダが最少のもの」を選ぶ方式では、右半分が巨大グラフィックの
セクション表紙が選ばれた。使用頻度で数えれば明確に判別できる（29枚 vs 1枚）。
並び順での決め打ちは当然危険。

**訂正4: `prs.slide_layouts` は先頭マスターの分しか返さない**
マスターが3つある資料（Google Slides由来）では、使用頻度2位のレイアウトが
2番目のマスターにいた。レイアウト探索は全マスターを走査する必要がある。

**訂正5: `run.font.name` はラテン用の指定を返す**
日本語主体の資料でも最頻出フォントが `Lexend Deca` や `Arial` になる。
これを本文フォントに採用すると日本語が化ける。CJK比率が3割を超えるなら
ラテン専用フォントを避けて選ぶ。

**フォントの扱い（D6の延長）**
テンプレートのフォントがLinux側に無い場合、字幅互換の代替があれば
`font_stack` に入れて計測に使い、`font`（pptxに書く名前）は元のままにする。
Arial→Liberation Sans、Calibri→Carlito など。
日本語フォントには字幅互換の代替が存在しないため、
`Meiryo UI` 等が指定されている場合は解決できず、`extract.py` が警告を出す。
**黙って別フォントで測って座標を狂わせるより、警告して人間に判断させる。**

**成果物の扱い**: 顧客資料そのもの（`templates/*.pptx`）と、そこから生成した
テーマ（社名・ブランド色を含む）はリポジトリに含めない。
匿名サンプル `themes/example-corporate.json` のみを追跡する。

### D12. テンプレート登録と生成は別処理として分ける
millet_ms に組み込む際のユースケースは「会社ごとにテンプレートを登録し、
後日それを使って何度もpptxを生成する」。登録と生成は性質が違う。

| | 登録 | 生成 |
|---|---|---|
| 頻度 | 稀 | 頻繁 |
| 対話性 | 人間のレビューあり | 全自動 |
| 入力 | 信用できない（顧客のアップロード） | 自社で管理 |
| 失敗の扱い | 4xxで返して直してもらう | 分類してリトライ判断（D10） |

**ベース化でスライドを全削除する。** マスターとレイアウトだけ残せばデザインは
完全に再現できる。狙いは容量削減（実測64〜96%）よりも
**顧客の機密スライドを保存しないこと**。提案資料には顧客名・金額・戦略が載っている。

**フォント判定は登録時に確定させる。** SaaSでは利用者がサーバーにフォントを
入れられないので、「このテンプレートは再現できない」ことを登録時に提示して
人間に決めさせる。生成のたびに警告が出る状態にはしない。
状態は `ok` / `substituted`（字幅互換）/ `approximated`（字幅不一致）/ `unavailable` の4つ。

**発行済みバージョンは書き換えない。** 過去に生成した資料を再現できるようにするため。
再登録は常に新バージョンになる。

**保管層はインターフェースで隔離する**（`TemplateStore`）。millet_ms では
メタデータをCloudSQL/Firestoreに置いた実装を注入する。
millet_ms の認証を `AuthProvider` で隔離したのと同じ方針。

### D13. ロゴ等のデザイン資産はベースpptxに内包したまま保管する
画像を別テーブル・別バケットで管理せず、ベースpptxの中に入ったままにする。
スライド削除で不要な画像は自動的に落ちるため、残るのは
マスター/レイアウトが参照する資産（ロゴ・透かし・背景）だけになる。
生成のたびに貼り直す処理も不要（マスター経由で自動的に乗る）。

- ベース実体は**内容ハッシュで重複排除**して保管し、メタが参照する。
  テンプレートは10〜20MBになり得るため、バージョンごとに丸ごと持つのは無駄
- そのため `pptx2base` は zip のタイムスタンプを固定し、
  **同じ入力なら常に同じバイト列**になるようにした。
  現在時刻が入ると秒をまたぐだけでハッシュが変わり重複排除が効かない
  （実測で発覚: 3バージョン登録して blob が2本できた）
- **ロゴがスライド側にしか無い資料では装飾が再現されない**。
  登録時に `design_warning` で通知する（実測7件中1件が該当）
- 容量の内訳は直感に反する。ある資料はベース11.35MBのうち10.53MBが
  埋め込みフォント22個で、画像は0.64MBだった。`assets.largest` で内訳を返す
- 埋め込みフォント（`.fntdata`）は難読化されており、描画側の計測には使えない

### D14. テンプレート確認は実物のラスタライズで行う
HTMLプレビューでは**マスター側の装飾（ロゴ・バナー・背景）が見えない**。
テンプレート登録の確認で見たいのは「ロゴと本文が一緒にどう見えるか」
「本文が装飾に被っていないか」なので、HTMLでは目的を達成できない。

実物のpptxを `soffice` でPDF化し `pdftoppm` でPNGにする。
そのため `libreoffice-impress` / `poppler-utils` をイメージに追加した。
バッチ側では使わないが、同一イメージで運用する方を選んだ（CI/CDが単純になる）。

- サンプルは3枚固定。soffice はpptx全体を変換するため枚数に比例して遅くなる
  （実測: 3枚で2.7〜3.6秒、67枚で23.5秒）
- キャッシュキーは**ベースの内容ハッシュ + テーマの内容**。テーマを編集して
  再確認する使い方をするため、テーマもキーに含める必要がある
- soffice はプロファイルを排他ロックするので、呼び出しごとに使い捨ての
  `-env:UserInstallation` を渡す。これをしないと同時実行で固まる
- LibreOfficeが無い環境（開発中のWSL等）では503を返し、UIはHTMLへ退避する

**実装中の発見**: プレビューで確認したところ、明示的に段落の揃えを
設定しないとテンプレート側の既定段落スタイル（`p:txStyles`）が漏れ出して
中央揃えになった。本パイプラインは配置・フォント・サイズ・揃えを
すべて明示指定しているため影響はないが、**テンプレートを使う場合は
「指定しなかったものはテンプレート側の設定が効く」**ことを意識する必要がある。

### D15. レイアウトに関わる値は原則すべて実測する（決め打ちの棚卸し）
実サンプルを1本作って目検したところ、**実測していなかった値が次々に問題を起こした**。
「実測できるものは実測する」という原則を掲げながら、抽出を作った順に
実測項目が増えただけで、体系的に洗い出していなかった。

実測に置き換えた項目（すべて目検で発覚）:

| 項目 | 決め打ちだった値 | 症状 |
|---|---|---|
| タイトルの位置 | `body_top - H*0.145` | ヘッダ帯の下に落ち、帯が空のまま残る |
| タイトルの高さ・文字サイズ | 固定44px | 帯の高さと合わない |
| 本文の文字サイズ | 固定22px | タイトル24pxと並び、見出しとの階層が崩壊 |
| 縦揃え | 常に上寄せ | 帯の中でタイトルが上に張り付く |
| 本文領域の起点 | `body_top` 固定 | 内容が少ないと下が大きく余る（使用率31%） |
| 下端の余白 | 固定40px | フッタ実測位置は27pxで、上下が非対称になる |
| pptxに書くフォント名 | 計測用フォント名を流用 | 閲覧側に無い代替名（Liberation Sans）を宣言していた |

**特に重要な誤り**: `font`（pptxに書く名前）と `font_stack`（計測用）を
分離したのに、`extract` が返す計測用フォント名をそのまま書き込んでいた。
「Arialと宣言しつつLiberation Sansで測る」という設計意図が失われていた。

**中央寄せの落とし穴**: 中央寄せ自体は正確でも、**領域が偏っていれば結果も偏る**。
`body_top` 起点の領域で中央寄せすると領域中心332px対画面中心270pxで下に寄った。
領域はタイトル下端からフッタ上端までを取るのが正しい。

**実測値どうしの整合**: タイトルと本文の位置は独立に判定するため、
タイトルが本文より下に来る資料が9件中2件あった。抽出後に整合を取る。

残っている決め打ち（影響が小さいか、テンプレート側に対応物がないもの）:
表のパディング、罫線幅、表の行高の安全マージン `×1.08`、
フロー図の角丸とgap、要素間の `margin-bottom`。

### D16. フロー図のボックスは等幅にする
幅を各ボックスに決めさせると、長い文のボックスだけ伸びて
中途半端な折り返し（最終行が1文字だけ）になる。`flex:1 1 0` で領域を等分する。
工程を表す箱の大小が文字数で決まるのは意味を持たない差でもある。

### 実装中に見つかった不具合（テストが捕まえたもの）
- **受入検査の順序**: 検査が `to_base` の中だけにあり、抽出の方が先に走っていた。
  壊れたファイルで python-pptx の例外が漏れて500になる。検査を最初に移動
- **グラフ種ごとのデータラベル位置**: 折れ線に `outEnd` を指定してPowerPointが
  「修復が必要」と表示した。積み上げ棒の `outEnd` が不正なことは対処済みだったが、
  折れ線も同じ制約を持つことに気づいていなかった。
  **より重大なのは CI をすり抜けたこと**。`pptx_check.py` の検証サンプルが
  縦棒1種類しか使っておらず、ゲートを置いた気になっていた。
  5種すべて（column/column_stacked/bar/line/pie）を生成してXMLを検査するよう修正。
  **ゲートを作るだけでなく、ゲートが実際に何を通しているかを確認する必要がある**
- **グラフサイズの固定値**: CSSで1000x380固定だったため、960x540のテンプレートで
  幅も高さも溢れた。キャンバス相対に変更
- **パレット1色でクラッシュ**: 抽出結果が1色になる資料は実在する
  （デザイン層に1色しかない）。2色目を前提にしていた箇所が2つあり、
  `theme.normalize()` で最低保証を入れ、グラフの系列色はパレットを循環させるようにした

**会社テンプレート適用の検証（実資料9件・全件成功）**

さらに2件で見つかった訂正:

### 実装上のハマりどころ（再発防止のため記録）

**python-pptx 全般**
- テキストボックスの `margin_*` を 0 にしないと座標が数mmずれる
- CSS px → pt は ×0.75（96dpi → 72pt）
- 箇条書きAPIが存在しない。`pPr` に `a:buFont` / `a:buChar` を直挿しする

**表**
- `first_row=False` / `horz_banding=False` を設定しないとテーマ由来の青い縞になる
- 行高は「最小値」でしかなく、PowerPoint が中身に応じて勝手に伸ばす。フォントメトリクス差の保険に +8%
- `cell.text = ...` は書式が飛ぶ。`run.text` に代入する
- **罫線APIが無い**。`tcPr` に `a:lnL/lnR/lnT/lnB` を直挿しする。
  `tcPr` の子要素順序は `ln* → fill → headers` で、破ると PowerPoint が修復を要求する。
  末尾追加ではなく `tcPr.insert(0, ln)` を逆順に回して順序を作る
- 線幅の下限は 0.25pt（3175 EMU）。それ未満は描画されない

**グラフ**
- `plot.vary_by_categories = False` を忘れると単系列が虹色になる（最頻出）
- 積み上げ棒で `OUTSIDE_END` は不正値。ファイルが壊れる
- `legend.include_in_layout = False` を忘れると凡例がプロット領域を侵食する

**フォント**
- CSS が要求する名前と実際にインストールされたフォント名は一致しない。
  `fonts-noto-cjk` が提供するのは `Noto Sans CJK JP` で、`Noto Sans JP` は存在しない。
  `fc-match "名前"` で確認する（フォールバックすると別名が返る）
- フォールバックは無警告で起きる。**沈黙して座標が全部狂うのが最悪のパターン**なので
  実行時チェックを必ず入れる

**Cloud Run**
- gVisor では `--no-sandbox --disable-dev-shm-usage` が必須
- uvicorn は `--workers 1` 固定。ブラウザをプロセス内共有しているため、
  workers を増やすと Chromium がワーカー数分立ち上がってメモリが死ぬ
- 日本語フォント（`fonts-noto-cjk`）をイメージに焼かないと全部豆腐になる
- コールドスタートの実体はプロセス起動ではなく**イメージPull**（Chromium入りで約2GB）

## 既知の制約と未実装

**制約（原理的なもの）**
- **閲覧者のPCに無いフォントは崩れる** → BIZ UDPGothic の採用で解決（D6）。
  別フォントを使う場合は「Windows標準搭載 かつ Linuxに導入可能」の条件を満たすこと
- グラデーション文字、`backdrop-filter`、`mask` 等は `raster` 送り
- 第2軸・複合グラフは python-pptx 実質未対応 → スライドを分割する
- Sankey・ネットワーク図は PowerPoint に存在しない → `raster`

**未実装**
- 表の結合セル（colspan/rowspan は抽出済み、ビルダーが未対応）
- フローの分岐・合流（現状は一直線のみ。菱形は置けるが枝分かれは未対応）
- フロー図のグループ化（`theme.flow.group` を用意したが未実装。
  グループにすると個別のボックスを触るのに一段手間が増えるため、手調整用途では不要かもしれない）
- 散布図・バブルチャート（`XyChartData` / `BubbleChartData` の別系統）
- スライドテンプレート集（`title-only` / 2カラム / 章区切り）
- `.potx` の直接読み込み（python-pptx の `valid_content_types` に無いため
  `[Content_Types].xml` の書き換えが必要。`.pptx` なら現状のまま使える）
- テンプレートの装飾を避けるセーフエリアの自動判定（現状は本文ブロックの実測とクランプ）
- 認証（Jobs はサービスアカウント + GCS IAM で足りる。Service を公開するなら別途）
- フォント埋め込み（python-pptx から触れないため XML 直書きが必要）
